## Build toolchain and target

- Round 2 used Android Gradle Plugin `9.1.1`, Gradle `9.3.1`, compileSdk `37`, and JDK `17`; Round 3 uses Android Gradle Plugin `9.5.0`, Gradle `9.9.1`, Kotlin/Compose compiler plugin `2.4.10`, KSP `2.3.12`, and JDK `21` for this verification environment.
- Round 3 compiles against stable Android API `36`, Build Tools `36.0.0`; it keeps `minSdk 30` and `targetSdk 30` for Android 11 sideloading. API 37 is excluded because the official Android 17 SDK setup page still labels it Preview.
- KSP `2.3.13` was not selected because its concurrent-execution regression is tracked in [Google KSP issue #3286](https://github.com/google/ksp/issues/3286); the build pins `2.3.12`.
- Final `--warning-mode all` tracing found one build-tool warning: KSP `2.3.12` calls Gradle's deprecated `Configuration.setVisible`. The upstream [KSP issue #3234](https://github.com/google/ksp/issues/3234) confirms the warning is in KSP plugin code; the [Gradle upgrade guide](https://docs.gradle.org/9.9.1/userguide/upgrading_version_9.html#deprecate-visible-property) says this setting has had no effect since Gradle 9 and is scheduled for removal in Gradle 11. KSP `2.3.13`'s [release notes](https://github.com/google/ksp/releases/tag/2.3.13) and [tagged source tree](https://github.com/google/ksp/tree/2.3.13) show the setter was removed, but that release has an open P1 concurrent-execution regression ([issue #3286](https://github.com/google/ksp/issues/3286)). We kept tested KSP `2.3.12` to avoid the reported code-generation risk; the Gradle 9.9.1 build succeeds. Revisit when KSP publishes a fix for #3286.
- Release has R8 minification and resource shrinking enabled. `abiFilters` is `armeabi-v7a`; packaging excludes `arm64-v8a`, `x86` and `x86_64`. Final APK inspection confirmed only `lib/armeabi-v7a/`.
- The requested API 30 target is for sideloading/testing, not a Play Store release; the specific expired-target lint is disabled. The release artifact is debug-certificate signed.

## Android alarm, accessibility and Xiaomi guidance

- Android’s [alarm scheduling guidance](https://developer.android.com/develop/background-work/services/alarms) recommends `setAlarmClock()` for a user-visible clock alarm. Round 2 uses `AlarmClockInfo` with a show-intent instead of the previous `setExactAndAllowWhileIdle()` path. Exact-alarm access is checked on API 31+; the target API remains 30.
- Android’s [wake-lock best practices](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock/best-practices) recommend bounded use and reliable release. The foreground announcement service uses a ten-minute partial wake lock, releases it on stop/destruction and logs failures.
- Android’s [`AccessibilityService` API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) documents screenshot access and callback constraints. Service binding/event callbacks are guarded and failures are written to the local diagnostic log. Screenshot failure codes are mapped to human-readable reasons, including secure window, rate limit and missing accessibility screenshot capability.
- Xiaomi’s [official Background autostart FAQ](https://www.mi.com/global/support/faq/details/KA-507611/) gives version-specific steps. Xiaomi does not publish a stable cross-version deep-link action for the Autostart page; the app opens general Android settings/app info and shows manual directions for Autostart, battery restrictions and locking in Recents rather than claiming a guaranteed subpage link.

## Device/architecture validation limits

The release APK contains `libandroidx.graphics.path.so`, `libdatastore_shared_counter.so`, `libjnidispatch.so`, `libmlkit_google_ocr_pipeline.so`, `libsqlcipher.so` and `libvosk.so`, all under `lib/armeabi-v7a/`. This proves packaging, not runtime compatibility on the Redmi. No Android 11/MIUI device, emulator or `adb` executable was available; alarm delivery, TTS voice availability, notification listener binding, accessibility/screenshot behavior, Vosk latency/RAM and reboot/force-stop behavior remain **UNTESTED** on the target.

## Round 3 Stage 2 Android API references

- WorkManager work requests support constraints and retry/backoff; periodic work is deferrable and can be delayed by constraints: [Define work requests](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [persistent background-work guide](https://developer.android.com/develop/background-work/background-tasks/persistent).
- Inline notification replies pass `RemoteInput` results in the Intent carried by a `PendingIntent`; reply is available only when the active notification exposes a reply action: [RemoteInput API](https://developer.android.com/reference/android/app/RemoteInput), [notification guide](https://developer.android.com/guide/topics/ui/notifiers/notifications).
- Floating windows require user-granted `SYSTEM_ALERT_WINDOW`, `Settings.canDrawOverlays`, and `TYPE_APPLICATION_OVERLAY`: [permission API](https://developer.android.com/reference/android/Manifest.permission), [window API](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_APPLICATION_OVERLAY).
- Secure app locking should use the platform system biometric prompt and explicitly declare allowed authenticators: [BiometricPrompt guide](https://developer.android.com/identity/sign-in/biometric-auth).
- Android cryptography guidance recommends AES-GCM and a provider only with Android Keystore; Security Crypto helper APIs are deprecated for new use: [cryptography guide](https://developer.android.com/privacy-and-security/cryptography).

### User-started floating overlay lifecycle

The overlay remains opt-in and only starts from a visible Settings tap. To keep an active floating window user-noticeable and stoppable on Android 11, the implementation uses a foreground service with an ongoing notification and notification Stop action, in addition to the visible overlay Stop button. Android 11 requires the user to grant `SYSTEM_ALERT_WINDOW` intentionally; its manage-overlay intent always opens the top-level Settings page and ignores package data, so the UI directs the user to select the app there. Sources: [Foreground services overview](https://developer.android.com/develop/background-work/services/fgs), [Android 11 permission changes](https://developer.android.com/about/versions/11/privacy/permissions).

Sources: [Android SDK platform releases](https://developer.android.com/tools/releases/platforms), [Android 17 SDK setup](https://developer.android.com/about/versions/17/setup-sdk), [Compose BOM 2026.06.01 POM](https://dl.google.com/dl/android/maven2/androidx/compose/compose-bom/2026.06.01/compose-bom-2026.06.01.pom), [Compose August 2026 stable release and API 37 requirement](https://android-developers.googleblog.com/2026/08/jetpack-compose-august-2026-release.html), and [OkHttp changelog](https://github.com/square/okhttp/blob/master/CHANGELOG.md).

## Round 4 platform references and compatibility choices (2026-11-11)

- **In-app speech input:** Android's [`SpeechRecognizer` reference](https://developer.android.com/reference/android/speech/SpeechRecognizer) documents the callback-based listener, explicit on-device availability APIs (API 33+), and lifecycle methods. [`RecognizerIntent`](https://developer.android.com/reference/android/speech/RecognizerIntent) documents the language, partial-results, and offline-preference extras. This app uses a callback listener and partial text, prefers `en-IN`, retries `en-US` only when the service reports an unsupported/unavailable language, and requests `EXTRA_PREFER_OFFLINE`; on API 30, whether speech works offline still depends on the installed recognizer and voice pack. Error hints are shown in the app. The Android speech service may ignore offline preference, so no offline guarantee is claimed.
- **Notification listener recovery:** Android's [`NotificationListenerService` reference](https://developer.android.com/reference/android/service/notification/NotificationListenerService) defines listener connected/disconnected callbacks and `requestRebind()` (API 24+). The implementation asks Android to rebind and, when still unbound, posts a component disable/enable cycle on the main thread. Recovery can still be prevented by MIUI settings or force-stop; only the user's Redmi test can establish whether this repair works on their firmware.
- **MIUI background guidance:** Xiaomi's [official Autostart FAQ](https://www.mi.com/global/support/faq/details/KA-507611/) provides version-dependent directions. The screen tells the user to review Background autostart, battery restrictions and the Recents lock; Xiaomi does not provide one stable deep link for these controls. WorkManager checks are periodic and deferrable, not a promise to run at exactly six hours.
- **System Clock handoff:** Android's [`AlarmClock` reference](https://developer.android.com/reference/android/provider/AlarmClock) documents `ACTION_SET_ALARM`, the hour/minute/message extras and `EXTRA_SKIP_UI`; the app declares `com.android.alarm.permission.SET_ALARM`. The setting defaults off, is used only for opted-in one-time alarms, and warns that the in-app alarm and Clock alarm may both ring. Actual Xiaomi Clock behavior remains **UNTESTED**.
- The project keeps its Round 3 stable pins and toolchain: compileSdk 36 (stable), minSdk/targetSdk 30, `armeabi-v7a` only, Compose BOM `2026.06.01`, Material 3 `1.4.0`, Room `2.8.5`, WorkManager `2.12.0`, Vosk Android `0.3.75`, bundled ML Kit Text Recognition `16.0.1`, PdfBox-Android `2.0.27.0`, and OkHttp `5.4.0`. No preview SDK, added ABI, or LLM dependency was introduced.


### Accessibility event capture for the opt-in macro recorder

- Android's official [`AccessibilityService` reference](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) says the system binds this service only after the user turns it on in Android settings, and documents the selected event types, callbacks and optional window-content capability. Android's [`AccessibilityEvent` reference](https://developer.android.com/reference/android/view/accessibility/AccessibilityEvent) defines window transitions, view clicks and text-change events; [`AccessibilityNodeInfo.isPassword`](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#isPassword()) identifies password-marked nodes. Round 4 captures only the app label, clicked text and non-password text additions while the user has explicitly started a macro recording; it holds steps in memory until Stop, and saves them only after the user's save action. It does not capture screenshots or log macro contents. Apps may omit, change or mark their accessibility events as sensitive; a real-phone test is required to check event behavior.
- Android's AccessibilityService reference says these services should assist users with disabilities. Round 4 remains a manually installed test APK; before any Google Play distribution, review current accessibility-service eligibility, disclosure and Play policy requirements. This is not a Play-policy approval.


### Performance profile and benchmark guidance

- The project includes `app/src/main/baseline-prof.txt` with three hand-authored hot-method rules (activity startup, ViewModel construction and encrypted database acquisition). It is not a device-generated Baseline Profile, and no app-specific speed gain is claimed. Android says Macrobenchmark should run in a separate `com.android.test` module on a `profileable` target and can generate Baseline Profiles; see the [Macrobenchmark overview and setup](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview), [Baseline Profile overview](https://developer.android.com/topic/performance/baselineprofiles/overview), and [profile generation guide](https://developer.android.com/topic/performance/baselineprofiles/create-baselineprofile). This environment has no attached Android 11 device or emulator, so a device-generated profile and cold-start/frame-time measurements were not feasible in this round.
